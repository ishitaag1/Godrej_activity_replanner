# Construction Schedule Intelligence

A local construction project-controls demonstration that expands a source-backed work sequence into a configurable multi-tower schedule, computes CPM dates and float, checks selected construction dependencies, and tests simultaneous delay events.

> **Synthetic data notice:** every record generated by this repository is synthetic. Default activity durations are editable illustrative assumptions, not approved project durations or actual Godrej Properties records. Actual starts, finishes, and progress are blank until a user enters or imports them.

## Purpose and use cases

- Expand construction work packages across configurable towers, floors, and unit counts.
- Edit durations, baseline dates, dependencies, and actual progress in a validated register.
- Inspect forecast dates, total/free float, critical activities, and critical paths.
- Apply one or more delay events together and compare the recalculated forecast with the baseline.
- Review selected sequence constraints extracted from `Construction_Activity_Sequence.docx`.
- Export/import the normalized register and save scenario comparisons.

The source document defines work order, not verified durations, crews, costs, or a project calendar. The editable master is [`templates/construction_sequence.json`](./templates/construction_sequence.json); the reproducible sample configuration is [`data/demo_project_config.json`](./data/demo_project_config.json). [`data/activities_demo.csv`](./data/activities_demo.csv) is the generated, normalized default schedule. The original 31-row `data/activities.csv` remains as a backward-compatibility fixture for the existing scheduler/assistant regression tests.

## Architecture

| File | Responsibility |
|---|---|
| `app.py` | Streamlit project overview, activity register, Gantt, dependency view, scenario controls, validation, progress and import/export |
| `scheduler.py` | Deterministic graph validation, forward/backward CPM, float, critical paths and simultaneous delay calculation |
| `activity_generator.py` | Config validation, repeatable template expansion, normalized CSV import/export |
| `sequence_validator.py` | Checks encoded sequence requirements without modifying user dependencies |
| `scenario_manager.py` | Saved scenario comparisons and explicitly non-optimized recovery review |
| `progress_tracker.py` | Status, remaining duration, forecast finish and overdue flags from supplied actual-progress data |
| `agent.py` | Optional local Ollama tool loop; scheduler results remain the source of truth |
| `templates/construction_sequence.json` | Editable package/activity templates and source-document references |
| `data/demo_project_config.json` | Synthetic two-tower / five-floor / two-unit demonstration configuration |
| `tests/` | Regression and feature tests |
| `.github/workflows/tests.yml` | Test suite on pushes and pull requests |

## Installation and setup (Windows PowerShell)

From a folder where you want to clone the project:

```powershell
git clone https://github.com/ishitaag1/Godrej_activity_replanner.git
cd .\Godrej_activity_replanner
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

If PowerShell blocks virtual-environment activation, run:

```powershell
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
```

## Run the application

```powershell
.\.venv\Scripts\Activate.ps1
python -m streamlit run app.py
```

Open the local URL printed by Streamlit (normally `http://localhost:8501`). The dashboard and deterministic scheduling features do not require Ollama.
The repository's `.streamlit/config.toml` hides Streamlit developer controls such as **Deploy**, while retaining viewer options.

Run the test suite:

```powershell
python -m unittest discover -s tests -v
```

## Configure and regenerate the sample

The sidebar provides project settings:

- Project start date
- Number of towers/wings
- Floors per tower
- Units per floor
- Applicable work packages
- Conditional activity templates to activate
- The retained-staircase material-shifting constraint

Select the reset confirmation before regenerating. Regeneration deliberately resets the active register and saved scenarios; it also establishes a new baseline. The default `data/demo_project_config.json` is reproducible and can be edited directly.

The generator expands package templates by scope:

- Project-wide setup, facade/external work and final inspection
- Tower-specific substructure, lift work, terrace and common-area cleaning
- Floor-specific RCC, blockwork and lobby cycles
- Unit-specific wet-area, room-finish and deep-cleaning workflows

IDs are deterministic, for example `T1-F05-SHELL-SLAB-POUR` and `T2-F03-U02-WET-WET-WATERPROOF`. Changing configuration changes the generated IDs and links deterministically. Every generated row includes the source reference, hierarchy/package fields, predecessors/successors, risk, condition metadata, baseline dates, explicit duration-assumption label, and `data_classification=Synthetic demonstration`. Actual progress and actual dates remain blank by default.

Conditional steps (for example backing plaster, optional false ceiling, external plaster, stone polishing, or excavation material categories) are absent unless activated. Excavation material categories are alternatives based on site evidence, not assumptions that all soil/rock types occur.

## Edit durations, dates, dependencies and progress

Use **Activity Register** to search/filter by ID/name, tower, floor, phase, trade, risk, status, and CPM criticality. Edit duration, milestone flag, predecessor IDs, baseline start, planned progress, actual start/finish and actual progress, then select **Apply register edits and recalculate**. Validation rejects invalid durations, missing predecessor IDs, and cycles. A failed edit does not replace the active schedule.

Durations must be positive whole calendar days, except a zero-day activity explicitly marked as a milestone. Milestones occur on one date and have no occupied duration; finish-to-start successors can start on that same date. Delay events extend task durations and are not applied to milestones. Dependency support is finish-to-start only; SS/FF/SF relationships and leads/lags are not implemented.

## CPM and calendar convention

- Whole **calendar days**; weekends and holidays count.
- For duration `D` and start `S`, inclusive finish is `S + (D - 1)`.
- A finish-to-start successor may start the next calendar day, `S + D`.
- Baseline start is an earliest-start floor; predecessor constraints can move an activity later.
- Forward pass computes ES and inclusive EF; backward pass computes LS and inclusive LF.
- Total float is `LS - ES`. Free float is the gap between an activity's exclusive finish and the earliest immediate successor start (or project finish for a sink).
- Zero total float indicates CPM criticality. Multiple critical chains are returned; the displayed `critical_path` remains a deterministic representative path for compatibility.
- Project duration counts both the first and last included calendar date.

The network engine validates duplicate IDs, missing predecessors, invalid dates/durations and cycles. It does not perform resource leveling, cost analysis, earned-value calculations, or working-day calendar calculations.

## Delay scenarios and scenario comparison

On **Delay Impact Analysis**, select several activity IDs and enter a separate non-negative whole-day delay for each. The engine increases those activity durations together, then computes CPM once on the combined network. It reports original/revised dates, completion slip, affected activities, float consumed, newly critical activities and critical-path changes. Delays can overlap; individual scenario impacts are not summed.

The single-delay `scheduler.apply_delay(...)` interface remains available as a wrapper. The baseline input frame is not mutated.

Save named scenarios in the session, compare them with baseline/current forecast, and export comparison rows as JSON or CSV. Saved scenarios are session-only and are cleared when the schedule is regenerated.

## Sequence validation and recovery review

`sequence_validator.py` checks encoded mandatory ordering, including MEP conduit before the relevant slab pour, post-pour clearance before dependent blockwork, plumbing first-fix before wet-area waterproofing, waterproofing before protective screed, terrace prerequisites, deep cleaning before final inspection, and the retained-staircase constraint. It reports the involved IDs, rule, severity, recommendation, and source reference. It never changes a user's graph.

Only relationships stated in or directly represented from the source are treated as mandatory. Relationships not represented in the templates are not guessed. The validator is a rule set for this template's recognized IDs, not a general natural-language document parser; unrecognized naming patterns should be reviewed manually.

**Recovery review is rule-based, not optimization.** It prioritizes zero-float activities for responsible-team review. It does not change sequencing, compress durations, add crews, or claim resource optimization.

## Progress tracking

Progress uses explicitly provided actual start/finish and actual progress values. The calendar is never used to infer actual completion or percentage. Remaining duration is estimated as `ceil(duration × (100 − actual progress %) / 100)` for activities with an entered actual percentage. Overdue is a date comparison against the current CPM finish and selected status date. No cost/EVM indicators are fabricated.

## Optional AI schedule assistant

To run the assistant locally, install Ollama and pull a model:

```powershell
copy .env.example .env
ollama pull llama3.2
```

Keep Ollama running and use the **AI Schedule Assistant** tab. It can call only the allow-listed tools in `agent.py` (project status, critical path, activity lookup/details and single-activity delay). The model cannot execute code or modify dependencies. Answers are marked scheduler-grounded only when a deterministic tool succeeds. If Ollama is unavailable, CPM, charts, validation and scenario analysis continue to work.

## Data import and export

The import tool expects the normalized generated-register columns, including IDs, hierarchy, phase, work package, predecessor/successor fields, duration, dates, progress, risk, conditional applicability and source/assumption metadata. CSV is validated before it replaces active data. The current activity register can be exported as CSV or JSON; saved scenario summaries can be exported as CSV or JSON.

The legacy `data/activities.csv` is a smaller compatibility fixture, not the detailed demonstration programme.

## Sample demonstration and expected behavior

1. Start the app with the default two towers, five floors per tower and two units per floor. The generated programme contains more than 1,000 synthetic activity records.
2. In the activity register, search `T1-F01-SHELL-MEP-CONDUIT` and verify that its slab pour is downstream.
3. In the delay page, add a delay to a critical activity and observe downstream date movement and completion slip.
4. Add a second delay event in another branch. The network is recalculated with both events together; overlap and float absorption are reflected in the result.
5. Choose a non-critical activity with sufficient float and apply a small delay; the project finish can remain unchanged.
6. Open **Sequence Validation** and confirm that a generated network has no encoded rule violations. Remove a predecessor in the register and rerun validation to see a rule reported.

Exact dates depend on selected optional work packages and edited durations. They remain synthetic and should not be presented as actual project performance.

## Interview demonstration guide

- **Problem:** Construction teams need a transparent way to see whether a local delay reaches handover.
- **Architecture:** A JSON activity master expands to a normalized, unique-ID register; `scheduler.py` computes all dates; Streamlit is the controls interface; the optional LLM only calls deterministic allow-listed tools.
- **Algorithm:** Explain inclusive calendar-day finish dates, forward/backward passes, total/free float, and criticality.
- **Scenario:** Select two delayed IDs, apply both at once, and compare the revised finish and critical paths with baseline.
- **Controls:** Show a sequence rule, one editable duration, an import/export validation, and progress left blank until actuals are supplied.
- **Limitations:** Synthetic durations, calendar days only, finish-to-start only, no resource/cost optimization, and no real project records.

## Known limitations

- Default durations are illustrative assumptions and are not calibrated against a real project.
- The sequence validator recognizes the IDs and dependency shapes generated from the bundled templates; it is not a complete document-understanding engine.
- Calendar days and finish-to-start dependencies only; no holidays, calendars, lags, leads, resource availability, costs, or earned value.
- Recovery suggestions are review prompts, not an optimized recovery plan.
- The Gantt limits the displayed selection for large networks; narrow the view by tower/floor/phase.
- The optional assistant requires a locally installed Ollama model and may produce ungrounded prose if no tool succeeds; only deterministic results are authoritative.
- A generated sample uses one retained staircase work package per tower; detailed staircase quantities and resource/access plans require project-specific configuration.
